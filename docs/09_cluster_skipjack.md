# Skipjack cluster (JHU ARCH): official docs + how we submit jobs

**Cluster-specific values live in `env/skipjack.sh`** (conda.sh path, HF cache, account `cxiao13`, partitions, `--comment=accept_cost`, the
`env -u SLURM_JOB_ID` quirk). Every job script loads them through `env/select.sh`; submit with `bash env/sb gpu|cpu [flags] <script>`
(see `docs/10_sync_workflow.md` §Running jobs). Logs land in `SRFT/slurm_logs/<jobname>_<jobid>.out`. Nothing below needs to be typed by hand
into a script any more; this file is the *explanation* behind those values.

## How this workspace is reached (user's ssh config)

  then tunnels to the allocated node's sshd via /dev/tcp. **This is where Claude Code normally runs (CPU node, e.g. csr048).**
- `skipjack-gpu` → ProxyCommand `~/vscode-gpu.sh` = `salloc -p h100 -t 04:00:00 --cpus-per-task=12 --gres=gpu:1 --account=cxiao13 --comment=accept_cost --job-name=vscode`

## Submitting GPU jobs from the compute-node shell (VERIFIED 2026-09-04)
The shell already sits inside slurm job `vscode` (`SLURM_JOB_ID` set, partition med, no GPU). Therefore:
- `srun --gres=gpu:1 …` / `--gpus` from this shell FAILS with `Invalid generic resource (gres) specification`
  (it tries to create a step inside the CPU allocation).
- **`sbatch` works directly from this shell** (verified job 312013: plain `sbatch plain_sbatch_test.sbatch` → A100 on ga137).
  sbatch only talks to the controller and creates a NEW job; it does not inherit the surrounding allocation.
  Clearing the variables is harmless and avoids surprises: `env -u SLURM_JOB_ID -u SLURM_JOBID sbatch my_job.sbatch` (jobs 311924, 312006).
- If you really need an interactive GPU step from here, use `salloc` (new allocation) rather than `srun`, or connect to `skipjack-gpu`.
- Template (cluster-neutral; account/partition/log path are added by `env/sb`):
  ```bash
  #!/bin/bash
  #SBATCH --gres=gpu:1            # or gpu:4
  #SBATCH -c 8 --mem=48G          # NOTE MaxMemPerCPU=6000 on GPU partitions: CPUs = ceil(mem/6 GB)
  #SBATCH -t 04:00:00             # max 3-00:00:00
  #SBATCH -J srft_eval
  SRFT_ROOT="${SRFT_ROOT:-$(d="${SLURM_SUBMIT_DIR:-$PWD}"; while [ ! -f "$d/env/select.sh" ] && [ "$d" != / ]; do d=$(dirname "$d"); done; echo "$d")}"
  source "$SRFT_ROOT/env/select.sh"                 # -> CONDA_SH, HF_HOME, SRFT_CLUSTER, ...
  source "$CONDA_SH" && conda activate agentdojo    # NOT "source ~/.bashrc": bashrc exits early in non-interactive batch shells
  cd "$SRFT_ROOT/agentdojo"
  ...
  ```
  Submit: `bash env/sb gpu my_job.sbatch` (adds `-A cxiao13 -p a100,h100,h200,l40s --comment=accept_cost -o slurm_logs/%x_%j.out`,
  and runs sbatch with the vscode job's SLURM vars cleared). Never `-o /tmp/...` (node-local).
- Monitoring: `squeue -u $USER` (the `vscode` job is our own shell; don't cancel it), `sqme`, `jobstats <id>`, `seff <id>`;
  live GPU use: `ssh <node> watch -n 1 nvidia-smi` or `srun --jobid=<id> --overlap nvidia-smi`.
- Alternative: `ssh skipjack` (login node) and run `sbatch` there normally; or open `skipjack-gpu` for interactive debugging.
- `/tmp` and `/dev/shm` are node-local; scratch `/weka/scratch/jhu/cxiao13/zwang544` (9.1 TB shared) is visible everywhere; home is 94 GB.

## Queue reality (2026-09-05)
GPU partitions can be saturated (seen: a100 250 pending, h100 273, h200 192, l40s 174, b200 2860; est. start next morning).
Mitigations that worked / are allowed: submit to several partitions at once `#SBATCH -p a100,h100,h200,l40s`; keep requests small
(1 GPU, ≤8 CPU, ≤64G) and short `-t` so backfill can slot them; `scontrol update jobid=<id> TimeLimit=00:45:00` on a pending job;
`squeue -j <id> --start` shows the scheduler's estimate. `bc` is not installed on the nodes.

## Who is clogging the GPU queue (all users)
```bash
# pending GPU jobs per user
squeue -p a100,h100,h200,b200,l40s -t PD -h -o "%u" | sort | uniq -c | sort -rn | head
# running jobs per user, and GPUs held per user
squeue -p a100,h100,h200,b200,l40s -t R -h -o "%u" | sort | uniq -c | sort -rn | head
squeue -p a100,h100,h200,b200,l40s -t R -h -o "%u %b" | awk '{split($2,a,":"); g[$1]+=a[length(a)]} END{for(u in g) print g[u], u}' | sort -rn | head
# full pending list of one partition (submit time, resources, reason)
squeue -p a100 -t PD -o "%.9i %.12u %.10P %.8T %.10l %.6D %.12b %.20S %R" | head -50
# one user's jobs
squeue -u <user> -o "%.9i %.10P %.8T %.10l %.12b %R" | head
# pending / running per partition
for p in a100 h100 h200 b200 l40s; do printf "%-5s pending=%-5s running=%s\n" $p $(squeue -p $p -h -t PD | wc -l) $(squeue -p $p -h -t R | wc -l); done
```

## Cost acceptance flag (enforced from 2026-09-08)
`sbatch` now rejects jobs with "Submission rejected: estimated cost ~$X. Resubmit with --comment=accept_cost or --export=ALL,ACCEPT_COST=1".
Every sbatch (including tiny CPU stats jobs) needs `--comment=accept_cost`; all our templates carry it, `submit_eval_sdL2.sh`'s stats job was
fixed the same day. Never hide sbatch stderr with `2>/dev/null` — a rejected job returns an empty id and the dependency chain silently breaks.

## QOS change (noticed 2026-09-08)
`sacctmgr show assoc user=$USER` now reports QOS `class` (default `class`); it was `all` before. Jobs submitted earlier under QOS=all sit forever
with reason `InvalidQOS` (our v2 stats job 329608 did) — cancel and resubmit (new jobs pick up the default automatically), or
`scontrol update jobid=<id> QOS=class`. Check with `squeue -o "%i %T %r %q"`.

## L40S memory limit for the parallel eval (2026-09-08)
2 HF-generate procs on one 46 GB L40S OOM'd on workspace (`torch.OutOfMemoryError`, one proc at 24 GB + the other) — long looping
trajectories reach 15 turns × ~8k tokens. Workspace shards now default to 1 proc/GPU in `submit_eval_sdL2.sh` (`WS_NPROC` to override);
banking/slack/travel/benign stay at 2. A crashed proc only loses its own tasks; resubmitting the same shard resumes.

## Scheduling gotchas (2026-09-09)
- `MaxMemPerCPU=6000` on the GPU partitions: a `--mem=64G` request silently becomes 11 CPUs, `--mem=96G` 16 CPUs. Busy GPU nodes often have 1–2 free GPUs but only 5–8 free CPUs, so a 1-GPU job with a big `--mem` waits for hours while `--mem=30G` (5 CPUs) starts. `scontrol update JobId=<id> MinMemoryNode=<MB>` fixes a pending job in place (CPU count follows).
- 2-GPU requests starved for 8 h on 2026-09-09 while 1-GPU jobs started in seconds. For ≤ 8k LoRA SFT use 1 GPU + `gradient_accumulation_steps=16`.
- Check free slots per node: `sinfo -p l40s -h -o "%n %t %C %e"` (CPUs A/I/O/T, free mem MB) and GPU use: `squeue -p l40s -h -t R -o "%b %N"`.
- (2026-09-11) Every sbatch now prints `cli_filter.lua: failed to load /etc/slurm/rates.lua … cost preview disabled` (and a `part_rates` lua
  error) on STDERR; the job is still submitted. Never capture sbatch's stderr into a job-id variable (`$(sbatch --parsable … 2>&1)`): the warning
  lands in `--dependency=afterany:<ids>` and the dependent job is rejected. Capture stdout only (`submit_eval_sdL2.sh` fixed the same day).
- QOS (checked 2026-09-09): defined = normal, scavenger, ssci, all, jhu, jsalt_2026, class, conda, rtx6000_condo, condo — ALL with priority 0, so QOS does not affect priority here. Our association (account cxiao13) allows only `class` (default; `all` was removed 2026-09-08 → old `all` jobs went InvalidQOS). Priority = age + fairshare + jobsize; our job 347215 = 7 + 3043 + 16. Other groups' jobs sit at ~18,000 because their FAIRSHARE is higher: account cxiao13 has used 31 % of the cluster's recent GPU-hours (EffectvUsage 0.31, FairShare 0.15, mostly user bsun39). ⇒ we are scheduled almost only by backfill into idle slots: keep requests small (1 GPU, mem = CPUs×6 GB, list every partition) and submit at night.
